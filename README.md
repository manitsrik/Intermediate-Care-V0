# ระบบบันทึกข้อมูลผู้ป่วย Intermediate Care

เว็บแอปให้บุคลากรกรอกแบบฟอร์มประเมินและดูแลผู้ป่วยในโปรแกรม Intermediate Care
โดยเก็บข้อมูลลง Google Sheet ของหน่วยงานโดยตรง สร้างด้วย Google Apps Script
จึงไม่ต้องเช่าเซิร์ฟเวอร์ และข้อมูลผู้ป่วยไม่ออกจากบัญชี Google ของโรงพยาบาล

อ้างอิงจากแบบฟอร์มกระดาษของกลุ่มงานเวชกรรมฟื้นฟู โรงพยาบาลกระบี่
(หน้า 1 ข้อมูลผู้ป่วยและตารางติดตาม หน้า 2 แบบประเมิน Barthel Index)

## ขั้นตอนติดตั้ง

1. สร้าง Google Sheet ใหม่ในบัญชี Google ที่จะใช้เก็บข้อมูล ตั้งชื่อเช่น `IMC Database`
2. วางข้อมูลเดิมจากไฟล์ `ตยเคส.xlsx` เป็นแท็บชื่อ **ตยเคส** ในไฟล์เดียวกัน (ถ้าจะนำเข้าข้อมูลเก่า)
3. เปิดเมนู **ส่วนขยาย → Apps Script**
4. สร้างไฟล์ตามรายการข้างบนแล้วคัดลอกเนื้อหาไปวางให้ครบ
   - ไฟล์ `.gs` สร้างเป็น Script ส่วนไฟล์ `.html` สร้างเป็น HTML
   - `appsscript.json` แก้ได้โดยเปิด **การตั้งค่าโปรเจกต์** แล้วติ๊ก *แสดงไฟล์ appsscript.json*
5. บันทึก แล้วกลับไปที่ Google Sheet **โหลดหน้าใหม่หนึ่งครั้ง** จะเห็นเมนู **Intermediate Care**
6. เลือก **Intermediate Care → ติดตั้งระบบ (ครั้งแรก)** ระบบจะสร้างชีตทั้งหมดให้
7. กลับไปที่ Apps Script เลือก **ทำให้ใช้งานได้ → การทำให้ใช้งานได้ใหม่ → เว็บแอป**
8. คัดลอกลิงก์เว็บแอปไปให้ทีมใช้งาน
9. แชร์ไฟล์ Google Sheet ให้ทีมทั้ง 5 คนในสิทธิ์ **ผู้แก้ไข**

### เรื่องสิทธิ์ของ deployment

`appsscript.json` ตั้งไว้เป็น `executeAs: USER_ACCESSING` และ `access: ANYONE`
เพราะช่วงทดสอบใช้บัญชี Gmail ส่วนตัวซึ่งไม่มีตัวเลือก "ทุกคนในองค์กร"

- แต่ละคนจะรันสคริปต์ด้วยบัญชีตัวเอง ระบบจึงบันทึกได้ถูกต้องว่าใครเป็นผู้กรอก
- ด้วยเหตุนี้ทุกคนต้องได้สิทธิ์ **ผู้แก้ไข** บนไฟล์ Sheet ด้วย
- `access: ANYONE` หมายถึงใครก็ตามที่มีลิงก์และล็อกอิน Google เปิดหน้าเว็บได้
  แต่จะใช้งานไม่ได้ถ้าอีเมลไม่อยู่ในแท็บ `users` ระบบจะปฏิเสธและแจ้งกลับไป

เมื่อย้ายไปบัญชี Google Workspace ของโรงพยาบาล ให้เปลี่ยนเป็น
`executeAs: USER_DEPLOYING` และ `access: DOMAIN` แล้ว deploy ใหม่
ทีมจะไม่ต้องมีสิทธิ์แก้ไขไฟล์ Sheet โดยตรงอีกต่อไป ซึ่งปลอดภัยกว่าสำหรับข้อมูลจริง

ถ้าถนัดใช้ command line ติดตั้ง [clasp](https://github.com/google/clasp) แล้วสั่ง
`clasp create --type sheets` และ `clasp push` จากโฟลเดอร์ `apps-script` ได้เช่นกัน

## การให้สิทธิ์ผู้ใช้

ทำที่หน้า **ตั้งค่า** ในแอป ไม่ต้องเปิดแท็บ `users` ในชีตเอง

- **เพิ่มผู้ใช้** กรอกอีเมล Google ชื่อ และสิทธิ์ ระบบแชร์ไฟล์ Sheet
  ให้ในสิทธิ์ผู้แก้ไขอัตโนมัติ ถ้าแชร์ไม่สำเร็จจะขึ้นสถานะเตือนไว้ในตาราง
- **สิทธิ์** มีสองระดับ `staff` ทำงานกับข้อมูลผู้ป่วยได้ทั้งหมด
  ส่วน `admin` จัดการผู้ใช้ในหน้านี้ได้เพิ่ม
- **แก้ชื่อ** พิมพ์ทับในช่องชื่อบนตารางได้เลย
- **ปิดการใช้งาน** ตัดสิทธิ์ทั้งในแอปและบนไฟล์ Sheet พร้อมกัน ชื่อยังอยู่ในตาราง
  ใช้กับคนที่ย้ายหรือลาออก จะได้ยังรู้ว่าเคยมีใครเข้าถึงข้อมูลผู้ป่วยบ้าง
- **ลบ** ใช้กับแถวที่ใส่ผิดตั้งแต่แรกเท่านั้น เช่นพิมพ์อีเมลผิดตัว
  ระบบจะถอนสิทธิ์ไฟล์ให้ก่อน ถ้าถอนไม่สำเร็จจะไม่ลบแถวทิ้ง
  เพื่อไม่ให้เหลือคนที่เปิดชีตดิบได้แต่ไม่มีชื่อค้างไว้ให้ใครสังเกต

ระบบกันไม่ให้ล็อกตัวเองออก คือปิดหรือลบบัญชีตัวเองไม่ได้
ลดสิทธิ์ผู้ดูแลของตัวเองไม่ได้ และต้องเหลือผู้ดูแลอย่างน้อย 1 คนเสมอ

ถ้ายังไม่มีใครในตาราง `users` เลย ระบบจะอนุญาตให้ทุกคนที่เปิดไฟล์ได้ใช้งานไปก่อน
เพื่อให้ติดตั้งครั้งแรกได้ พอเพิ่มรายชื่อแล้วจะบังคับตรวจสิทธิ์ทันที
และถ้ามีคนในตารางแล้วแต่ยังไม่มีใครเป็น `admin` หน้าตั้งค่าจะมีปุ่มให้ตั้งตัวเอง
เป็นผู้ดูแลคนแรก แล้วช่องทางชั่วคราวนี้จะปิดทันที

## โหมดทดสอบและ PDPA

โหมดทดสอบเปิดอยู่ตอนนี้ หมายความว่า

- ตอนนำเข้าข้อมูลเดิม ชื่อจะกลายเป็น `ทดสอบ 1`, `ทดสอบ 2`
  HN กลายเป็น `TEST001`, `TEST002` ที่อยู่กลายเป็น `xxx`
  เบอร์โทรเหลือ 3 ตัวแรกแล้วต่อด้วย `xxx-xxxx`
- หน้าเว็บจะขึ้นแถบเตือนสีเหลืองว่ากำลังใช้ข้อมูลสมมติ

ผู้ดูแลระบบสลับโหมดนี้เองได้ที่หน้า **ตั้งค่า** ไม่ต้องแก้โค้ดแล้ว push ใหม่
ค่าที่สลับไว้เก็บใน Script Properties ส่วน `CONFIG.MASK_MODE` ใน `Config.gs`
เหลือหน้าที่เป็นค่าตั้งต้นของไฟล์เท่านั้น โค้ดทุกที่อ่านค่าที่ใช้จริงผ่าน `maskMode_()`

สวิตช์นี้มีผลกับแถบเตือนบนหน้าจอ และกับการนำเข้าข้อมูลครั้งถัดไป
**ข้อมูลที่นำเข้าไปแล้วถูกปกปิดตั้งแต่ตอนเขียนลงชีต ปิดโหมดทีหลังไม่ได้คืนค่าจริงให้**

เมื่อจะใช้งานจริง

1. ย้ายไฟล์ไปอยู่ใน Shared Drive หรือบัญชี Google Workspace ของโรงพยาบาล
2. แจ้งผู้รับผิดชอบข้อมูลส่วนบุคคลของโรงพยาบาลให้รับทราบก่อนเริ่มเก็บข้อมูลจริง
3. จำกัดสิทธิ์การเข้าถึงไฟล์เป็นรายบุคคล อย่าใช้ตัวเลือก "ทุกคนที่มีลิงก์"
4. **ล้างข้อมูลทดสอบออกก่อน** ด้วยเมนู **Intermediate Care → ล้างข้อมูลที่นำเข้ามา**
   แล้วค่อยปิดโหมดทดสอบที่หน้าตั้งค่า

## การนำเข้าข้อมูลเดิม

เลือกเมนู **Intermediate Care → นำเข้าข้อมูลเดิมจากชีต ตยเคส**

ไฟล์เดิมมีปัญหาที่ตัวนำเข้าจัดการให้อัตโนมัติ

- **วันที่เพี้ยนเป็นปี ค.ศ. 19xx** เพราะพิมพ์ปี พ.ศ. สองหลักแล้วโปรแกรมตีความเป็น ค.ศ.
  เช่นเลข `25132` คือ 21 ต.ค. 1968 ระบบจะแปลงกลับเป็น 21 ต.ค. 2568
- **รูปแบบวันที่ปนกันหลายแบบ** ทั้งเลข serial, `27/10/68` และ `01 พฤษภาคม 2569`
- **ข้อมูลอยู่ผิดคอลัมน์** เช่นช่อง `BI4` เก็บวันที่ หรือช่อง `วันที่End` เก็บคะแนน BI
  ระบบใช้เกณฑ์ว่าคะแนน BI ต้องเป็นจำนวนเต็ม 0 ถึง 20 เท่านั้น ถ้าเกินถือว่าเป็นวันที่ที่หลุดมา
- **ที่อยู่ถูกแปลงเป็นวันที่** เช่นบ้านเลขที่ `3/11` ระบบจะกู้กลับเป็นข้อความ
- **เบอร์โทรสองเบอร์ในช่องเดียว** จะถูกแยกเป็น `phone1` และ `phone2`
- **คำสะกดไม่ตรงกัน** เช่น `Recerrent stoke` แก้เป็น `Recurrent stroke`

กรณีที่ระบบเดาไม่ได้ เช่น `ยบ.IMC 11/11` ที่ไม่มีปีกำกับ จะไม่เดาให้
แต่บันทึกไว้ในแท็บ `migration_report` พร้อมบอกว่าเป็นแถวไหน ช่องอะไร ค่าเดิมคืออะไร
เพื่อให้เจ้าหน้าที่กลับไปตรวจกับแฟ้มจริง

## โครงสร้างข้อมูล

| ชีต | 1 แถวคือ |
|---|---|
| `patients` | ผู้ป่วย 1 ราย ใช้ HN เป็นกุญแจ ท้ายแถวมี `bi_1..bi_5` คัดลอกคะแนนแต่ละครั้งมาไว้ให้ชีต summary ดึงตรง ๆ |
| `bi_assessments` | การประเมิน BI 1 ครั้ง เก็บคะแนนราย 10 ข้อ ไม่ใช่แค่ผลรวม |
| `followups` | การติดตาม 1 ครั้ง (PT เยี่ยมบ้าน OPD โทรติดตาม) |
| `users` | ผู้มีสิทธิ์ใช้งาน |
| `summary` | มุมมองรวมหน้าตาใกล้เคียงไฟล์เดิม สร้างจากสูตรล้วน ห้ามพิมพ์ทับ ทุกสูตรเป็นการดึงค่าจาก `patients` แถวต่อแถว ไม่มีตัวไหนค้นข้ามตาราง ชีตจึงไม่อืดเมื่อข้อมูลโต |
| `migration_report` | จุดที่ต้องกลับไปตรวจกับแฟ้มจริงหลังนำเข้า |

ตารางแยกกันแบบนี้ทำให้บันทึก BI และการติดตามได้ไม่จำกัดจำนวนครั้ง
ต่างจากไฟล์เดิมที่มีช่องให้แค่ 5 ครั้ง ทั้งที่ฟอร์มกระดาษเผื่อไว้ 10 ครั้ง

## หน้ารายชื่อผู้ป่วย

หน้าที่ทีมเปิดบ่อยที่สุด เปิดแอปแล้วมาที่นี่เป็นหน้าแรก จึงต้องตอบให้ได้ว่า
**วันนี้ต้องตามใคร** ไม่ใช่แค่บอกว่ามีใครอยู่ในระบบบ้าง

### คอลัมน์งานค้าง

ท้ายตารางมีคอลัมน์ติดป้ายว่าผู้ป่วยรายนั้นค้างเรื่องอะไรอยู่ ค้างหลายเรื่องพร้อมกันได้
ป้ายใช้คำสั้นเพราะช่องมีที่ให้ไม่กี่ตัวอักษร เอาเมาส์ไปวางแล้วเห็นคำเต็ม

| ป้ายบนแถว | สี | คำเต็ม |
|---|---|---|
| เลยนัด | ส้ม | เลยกำหนดนัดแล้ว |
| ครบกำหนด | ส้ม | ครบกำหนดโปรแกรมแล้ว ยังไม่ปิดเคส |
| ค้างประเมิน BI | ส้ม | ไม่ได้ประเมิน BI เกิน 8 สัปดาห์ |
| ต้องปิดเคส | ส้ม | คัดกรองออกแล้ว ยังไม่ปิดเคส |
| ไม่มีวันสิ้นสุด | เทา | ปิดเคสแล้วแต่ไม่มีวันสิ้นสุด |

คำสองแบบนี้เก็บคู่กันไว้ที่ `ATTENTION` ใน `Config.gs` ที่เดียว ป้ายบนแถวกับบรรทัด
ในกล่อง "ต้องจัดการ" บนแดชบอร์ดจึงไม่มีทางพูดคนละเรื่อง เวลามีใครแก้ข้อความข้างใดข้างหนึ่ง

### ทำไมสีไม่เหมือนกันทุกป้าย

`ATTENTION` กำกับ `kind` ไว้ให้ทุกข้อ แยกงานสองชนิดที่ไม่ควรนับรวมกัน

| kind | คือ | ทำเมื่อไหร่ | ป้าย |
|---|---|---|---|
| `care` | กระทบคนไข้ที่ยังดูแลอยู่ | วันนี้ | ส้ม |
| `data` | ช่องที่ต้องไล่เติมจากแฟ้มเก่า | ตอนว่าง | เทา |

เหตุผลมาจากข้อมูลจริง ตอนเปิดใช้รอบแรกมีผู้ป่วย 59 ราย แต่ติดธง 54 ราย
เพราะเคสเก่าที่ปิดไปแล้วเกือบทั้งหมดไม่มีวันสิ้นสุด (มาจากไฟล์ที่นำเข้า)
ตัวเลขไม่ผิด แต่พอเป็น 92% ของทั้งระบบก็เอาไปวางแผนวันนี้ไม่ได้
และถ้าย้อมส้มทุกแถวเหมือนกันหมด ตาจะเลิกมองป้าย แล้วรายที่ต้องรีบจริงจะหายไปกลางกอง

บรรทัดใต้ชื่อหน้าจึงแยกเป็นสองก้อน **มีงานค้าง** นับเฉพาะ `care`
ส่วน **ข้อมูลต้องเติม** นับ `data` เป็นคนละงานของคนละคนคนละเวลา

เวลาเพิ่มธงใหม่ ให้ถามก่อนว่าคนอ่านต้องลุกไปทำอะไรกับคนไข้หรือเปล่า
ถ้าใช่คือ `care` ถ้าเป็นเรื่องความครบของข้อมูลคือ `data`

ธงเองมาจาก `attentionFlags_()` ซึ่งตอนนี้ถูกเรียกใน `displayPatient_()` ที่เป็นทางผ่าน
ของผู้ป่วยทุกรายก่อนออกจากเซิร์ฟเวอร์ ทั้งหน้ารายชื่อ แดชบอร์ด รายงาน และรายชื่อในโมดัล
จึงอ่านธงชุดเดียวกัน ไม่มีหน้าไหนตีความคำว่า "ค้าง" เป็นของตัวเอง
เดิมมีแต่แดชบอร์ดที่คำนวณธงนี้ หน้ารายชื่อจึงเป็นหน้าที่คนเปิดทุกวันแต่บอกน้อยที่สุด

### ตัวกรอง

| ช่อง | เลือกได้ |
|---|---|
| ค้นหา | HN, เลขประจำตัว, ชื่อ, นามสกุล, ตำบล, Dx |
| สถานะ | กำลังดูแล / จบโปรแกรมแล้ว |
| ผลคัดกรอง | เข้า IMC / ไม่เข้าเกณฑ์ / **ยังไม่ประเมิน** |
| งานค้าง | **งานค้างของเคสที่ยังดูแลอยู่** / มีงานค้าง (รวมข้อมูลต้องเติม) / เจาะรายข้อตามตาราง / ยังไม่เคยประเมิน BI |

ตัวเลือกแรกของช่องงานค้างคือทางลัดที่คนเปิดตอนเช้าน่าจะใช้บ่อยที่สุด
กรองเอาเฉพาะ `care` ไม่ปนกับเคสเก่าที่ค้างแค่วันสิ้นสุด

ตัวเลือก **ยังไม่ประเมิน** สำคัญกว่าที่เห็น เพราะช่อง `screening_result` ที่ยังว่าง
คือคนที่ยังไม่มีใครไปคัดกรอง ซึ่งเป็นกลุ่มที่ต้องตามงานที่สุด แต่เดิมกรองแยกออกมาไม่ได้เลย
ต้องกวาดตาหาเองจากรายชื่อทั้งหมด

**ยังไม่เคยประเมิน BI** อยู่ในดรอปดาวน์งานค้างแต่ไม่ใช่ธงงานค้าง เพราะรายที่เพิ่งลงทะเบียน
เมื่อวานยังไม่ถือว่าค้าง แต่เป็นช่องที่ต้องตามให้ครบอยู่ดี จึงให้เลือกดูได้จากที่เดียวกัน

ตัวกรองทั้งหมดทำงานในเครื่อง ไม่ยิงไปเซิร์ฟเวอร์ต่อการกดหนึ่งครั้ง
กรองจนไม่เหลือใครจะมีปุ่มล้างตัวกรองให้ ส่วนตอนยังไม่มีผู้ป่วยในระบบเลย
จะชวนลงทะเบียนเคสแรกแทน สองกรณีนี้ว่างคนละแบบ จึงไม่ควรขึ้นข้อความเดียวกัน

### ส่งออกรายชื่อ

ปุ่มในหัวหน้าส่งออกเฉพาะรายที่ตัวกรองเหลืออยู่ ไม่ใช่ทั้งฐาน ตัวเลขบนปุ่มบอกจำนวนที่จะได้
คอลัมน์ในไฟล์เป็นชุดเดียวกับที่ส่งออกจากหน้ารายงานและจากโมดัลรายชื่อ (`EXPORT_COLS`)
รวมคอลัมน์งานค้างซึ่งเขียนเป็นคำเต็มภาษาไทย ไม่ใช่รหัสอย่าง `appt`

## แดชบอร์ดตามพื้นที่ผู้ป่วย

เลือก **ทุกพื้นที่ / ทั้งจังหวัดกระบี่ / ต่างจังหวัด / ยังไม่ระบุพื้นที่** แล้วเลือกอำเภอ
เมื่อเลือกอำเภอใดก็ตามในกระบี่ จะเลือกตำบลของอำเภอนั้นต่อได้ ครบทั้ง 8 อำเภอ 53 ตำบล
การ์ดสถิติ กราฟ ผลคัดกรอง นัดหมาย และค่าเปรียบเทียบเดือนก่อนคำนวณจากกลุ่มเดียวกันทั้งหมด

ตัวกรองอยู่แถวเดียวกับหัวข้อ "แดชบอร์ด IMC" กับกล่องวันที่ ไม่แยกเป็นแถบของตัวเอง
กดจำนวนรายเพื่อดูรายชื่อผู้ป่วยในพื้นที่ที่เลือกอยู่ เปิดเวชระเบียนหรือส่งออก CSV
พร้อมจังหวัด อำเภอ และตำบลได้ ส่วน **ล้าง** กลับไปดูทุกพื้นที่
บนมือถือดรอปดาวน์ถูกซ่อนไว้ เหลือชื่อพื้นที่ จำนวนผู้ป่วย และปุ่ม **เลือกพื้นที่**

ตัวกรองนี้ไม่ได้อยู่บนแถบบนของแอป ทั้งที่ตรงนั้นมีที่ว่าง เพราะแถบบนอยู่นอก `<main>`
จึงค้างอยู่ทุกหน้า ส่วนตัวกรองนี้มีผลแค่แดชบอร์ด ถ้าเอาขึ้นไปวาง คนเปิดหน้ารายชื่อผู้ป่วย
จะเห็นชื่ออำเภอค้างอยู่บนหัวแล้วเข้าใจว่ารายชื่อข้างล่างถูกกรองแล้ว ทั้งที่ไม่ใช่
ถ้าวันหนึ่งอยากให้พื้นที่เป็นตัวกรองร่วมของทั้งระบบ ต้องทำให้หน้าอื่นกรองตามด้วยก่อน
แล้วค่อยย้ายขึ้นไป

เคยมีปุ่ม **สรุปพื้นที่** ที่เปิดตารางเทียบทุกอำเภอ/ตำบลพร้อมกัน เอาออกจากแดชบอร์ดแล้ว
เพราะไปเบียดอยู่บนแถบเดียวกับดรอปดาวน์ที่ทำเรื่องพื้นที่เหมือนกัน ทั้งที่คนละหน้าที่
ตอนนี้ตารางเทียบพื้นที่ไปอยู่ที่หน้ารายงาน / BI ในชื่อ **แจกแจงรายอำเภอ**
ซึ่งเป็นที่รวมของแท่งเทียบกลุ่มอยู่แล้ว และเทียบกับกลุ่ม ADL ได้ในตารางเดียว
ส่วน `districts` กับ `tambons` ที่แดชบอร์ดคำนวณส่งมายังอยู่ครบและมีเทสต์คุมเหมือนเดิม

ฟอร์มผู้ป่วยเพิ่มช่อง `province` และ `district` เมื่อกรอกจังหวัดกระบี่
อำเภอและตำบลเป็นตัวเลือกที่สัมพันธ์กัน ต่างจังหวัดกรอกชื่อพื้นที่เป็นข้อความได้
เมื่อเปลี่ยนจังหวัดหรืออำเภอจะล้างตัวเลือกพื้นที่ย่อย เพื่อไม่ให้ค้างค่าของพื้นที่เดิม
API ตรวจความสัมพันธ์อีกครั้งก่อนบันทึก

**ข้อมูลเก่า:** ตอนแสดงผลไม่อนุมานจังหวัดจากชื่อตำบลหรือข้อความที่อยู่
เพราะชื่อตำบลซ้ำข้ามจังหวัดได้ รายการที่ไม่ยืนยันจังหวัด/อำเภออยู่ในกลุ่ม
**ยังไม่ระบุพื้นที่** ส่วนรายที่รู้อำเภอแต่ไม่มีตำบลหรือตำบลไม่ตรงรายชื่อ
อยู่ในกลุ่ม **ยังไม่ระบุตำบล / ต้องตรวจสอบ**
เปิดรายชื่อแล้วแก้ที่อยู่ทีละรายได้ การเปิดหรือแก้ข้อมูลด้านอื่นไม่ลบที่อยู่เดิม

เมนู **Intermediate Care → เติมจังหวัด/อำเภอจากชื่อตำบล** เติมย้อนหลังให้ทีเดียวได้
โดยเทียบชื่อตำบลกับรายชื่อใน `Geography.gs` ตำบลทั้ง 53 แห่งของกระบี่ไม่มีชื่อซ้ำกัน
จึงระบุอำเภอได้ตัวเดียวแน่นอน เติมเฉพาะรายที่ยังไม่มีทั้งจังหวัดและอำเภอ
ของที่กรอกไว้แล้วไม่แตะ และเติมเฉพาะชื่อที่ตรงกับตำบลในกระบี่เท่านั้น
ที่เหลือปล่อยว่างพร้อมรายงานชื่อตำบลที่เดาไม่ได้ ให้ไปตรวจกับแฟ้มจริงเอง
ดีกว่าเดาผิดแล้วสถิติรายพื้นที่เพี้ยนโดยไม่มีใครรู้ตัว เรียกซ้ำได้ ผลลัพธ์เท่าเดิม

เมื่อเปิดแอปหลังเผยแพร่เวอร์ชันนี้ ระบบจะเพิ่มหัวคอลัมน์ `province`, `district`
ที่ต่อท้าย `bi_1..bi_5` ให้อัตโนมัติโดยไม่เลื่อนหรือเขียนทับข้อมูลเดิม
ยังสามารถเรียก `setupSystem()` เพื่อซ่อมโครงสร้างชีตทั้งหมดด้วยตนเองได้ตามปกติ
การอัปเดตนี้ไม่เติมจังหวัด/อำเภอให้ข้อมูลเก่าอัตโนมัติ
ไม่จำเป็นต้องแก้ PWA หรือลิงก์ deployment สำหรับฟีเจอร์นี้

รายชื่อพื้นที่อ้างอิงตารางผนวก 1 ของกรมพัฒนาที่ดิน
[หน้า 33](https://e-library.ldd.go.th/library/flip/bib10629f/files/basic-html/page36.html)
และ [หน้า 34](https://e-library.ldd.go.th/library/flip/bib10629f/files/basic-html/page37.html)
เก็บไว้ใน `Geography.gs` เพื่อใช้งานโดยไม่เรียกข้อมูลภายนอกขณะเปิดแอป

## กราฟเข้าใหม่และจบโปรแกรม

หนึ่งงวดมีสองแท่ง สลับดูรายเดือน / รายไตรมาส / รายปีงบได้

- **แท่งซ้าย เข้าใหม่** นับจาก `start_date` แบ่งชั้นตามผลคัดกรอง
  เข้าเกณฑ์ IMC / ไม่เข้าเกณฑ์ / ยังไม่คัดกรอง (ชั้นสุดท้ายโผล่เฉพาะตอนมีจริง)
  ใช้สีชุดเดียวกับโดนัทผลการคัดกรอง เพื่อให้สองที่อ่านเป็นภาษาเดียวกัน
- **แท่งขวา จบโปรแกรม** นับจาก `end_date` เฉพาะเคสที่ปิดแล้ว

**สองแท่งนี้นับจากคนละช่องวันที่** ผู้ป่วยหนึ่งคนจึงอยู่คนละงวดกันได้
เช่นเริ่ม ส.ค. แล้วจบ ก.ย. แท่งเข้าใหม่จะขึ้นที่ ส.ค. ส่วนแท่งจบขึ้นที่ ก.ย.
บรรทัดใต้หัวกราฟเขียนกำกับไว้เสมอ ห้ามตัดออก ไม่งั้นคนอ่านจะเหมาว่าทั้งกราฟนับจากวัน Start

ที่ต้องมีสองแท่งเพราะตัวเลข "กำลังดูแล" บอกได้แค่ ณ วันนี้ ไม่บอกว่ากำลังพุ่งขึ้นหรือทรงตัว
ถ้าแท่งเข้าใหม่สูงกว่าแท่งจบติดกันหลายงวด แปลว่าภาระงานสะสมขึ้นเรื่อย ๆ

กดแท่งไหนก็เปิดรายชื่อกลุ่มนั้นได้ แท่งจบโปรแกรมให้รายชื่อ "คนที่จบในงวดนี้"
ซึ่งเดิมไม่มีทางเปิดดูจากหน้าไหนเลย

## กล่อง "ต้องจัดการ" บนแดชบอร์ด

การ์ดสถิติสามใบบอกสถานการณ์ว่างานมีเท่าไรและได้ผลแค่ไหน แต่ไม่บอกว่าวันนี้ต้องทำอะไร
กล่องนี้จึงหยิบเคสที่ค้างขึ้นมาเตือน แยกบรรทัดตามเหตุผล กดแล้วเปิดรายชื่อกลุ่มนั้นได้ทันที

| บรรทัด | เงื่อนไข |
|---|---|
| เลยกำหนดนัดแล้ว | `kbh_appt_date` ผ่านไปแล้ว |
| ครบกำหนดโปรแกรมแล้ว ยังไม่ปิดเคส | `imc_end_date` ผ่านไปแล้ว |
| ไม่ได้ประเมิน BI เกิน 8 สัปดาห์ | `latest_bi_date` ห่างเกิน `CONFIG.BI_STALE_DAYS` ถ้ายังไม่เคยประเมินนับจากวัน Start |
| คัดกรองออกแล้ว ยังไม่ปิดเคส | `screening_result` เป็น NoIMC |
| ปิดเคสแล้วแต่ไม่มีวันสิ้นสุด | ปิดเคสแล้วแต่ `end_date` ว่าง |

ห้าบรรทัดแรกนับเฉพาะเคสที่ยังไม่ปิด เพราะเคสที่ปิดแล้วไม่มีอะไรต้องทำต่อ
ส่วนบรรทัดสุดท้ายกลับกัน นับเฉพาะเคสที่ปิดไปแล้วแต่ไม่มีวันสิ้นสุด
ฟอร์มจบโปรแกรมในแอปบังคับกรอกวันที่อยู่แล้ว ที่ขาดจึงมาจากข้อมูลนำเข้าเป็นหลัก
เคสพวกนี้ยังนับเป็น "จบแล้ว" บนการ์ด แต่**หายไปจากแท่งจบโปรแกรมบนกราฟ**
ทำให้กราฟดูเหมือนไม่มีใครจบเลยทั้งที่จบไปแล้ว จึงต้องไล่เติมวันที่จากแฟ้มจริง
บรรทัดที่ยอดเป็นศูนย์จะไม่แสดง ถ้าไม่ค้างเลยกล่องจะบอกว่าไม่มีงานค้าง
ตัวเลขกับรายชื่อที่กดเข้าไปดูมาจากธงชุดเดียวกันที่ `attentionFlags_()` ติดไว้กับผู้ป่วยแต่ละราย
จึงไม่มีทางนับไม่ตรงกัน และกล่องนี้ใช้ตัวกรองพื้นที่เดียวกับทั้งแดชบอร์ด
ธงชุดเดียวกันนี้ยังไปโผล่เป็นป้ายบนแถวในหน้ารายชื่อผู้ป่วยด้วย กล่องนี้ตอบว่า
"ค้างกี่ราย" ส่วนหน้ารายชื่อตอบว่า "รายนี้ค้างอะไร" ระหว่างที่กำลังดูเคสอยู่

บรรทัด "คัดกรองออกแล้ว ยังไม่ปิดเคส" มีไว้ดูความสะอาดของข้อมูลเป็นหลัก
ถ้ามีเยอะแปลว่ามีเคสที่คัดกรองออกไปแล้วแต่ลืมปิด ทำให้ยอด "กำลังดูแล" สูงเกินจริง

## แดชบอร์ดกับหน้ารายงานต่างกันอย่างไร

สองหน้านี้ตอบคนละคำถาม จึงจัดของคนละแบบ

| | แดชบอร์ด | รายงาน / BI |
|---|---|---|
| ตอบคำถาม | ตอนนี้เป็นยังไง และต้องทำอะไร | ดูแลแล้วได้ผลไหม และคนไข้กลุ่มนี้หน้าตาเป็นแบบไหน |
| แกนหลัก | เวลา — เดือนนี้ เทียบเดือนก่อน นัดที่จะถึง ที่เลยกำหนด | ผลลัพธ์และองค์ประกอบ — สัดส่วนของแต่ละกลุ่ม |
| ใช้ตอนไหน | เปิดทุกวัน | ตอนสรุปส่งรายงาน |
| ตัวเลขเป็น | จำนวนที่ต้องลงมือ | ร้อยละของกลุ่ม |

เวลาจะเพิ่มของใหม่ ให้ถามก่อนว่ามันตอบคำถามข้อไหน แล้ววางในหน้านั้น
กล่อง "ต้องจัดการ" จึงอยู่บนแดชบอร์ด ส่วนแท่งสรุปเหตุจบอยู่หน้ารายงาน

ทั้งสองหน้าใช้ตัวกรองพื้นที่ชุดเดียวกัน สร้างจาก `areaSelects()` ตัวเดียวกัน
เปิดหน้ารายงานครั้งแรกจะสืบทอดพื้นที่ที่เลือกไว้บนแดชบอร์ดมาให้ ไม่ต้องเลือกซ้ำ
และไม่เผลออ่านเลขทั้งจังหวัดว่าเป็นเลขของอำเภอที่เพิ่งดูอยู่

## หน้ารายงาน / BI

หน้านี้ตอบสองคำถามเรียงกันจากบนลงล่าง **ดูแลแล้วได้ผลไหม** แล้วค่อย
**คนไข้กลุ่มนี้หน้าตาเป็นแบบไหน** แถวการ์ดตัวเลขบนสุดคือคำตอบ
ส่วนแท่งกับตารางข้างล่างคือคำอธิบายว่าตัวเลขนั้นมาจากไหน

### หัวหน้าสามชั้น

หัวหน้ารายงานอยู่ในกรอบเดียว แบ่งเป็นสามชั้นอ่านเรียงจากบนลงล่าง

| ชั้น | มีอะไร |
|---|---|
| บน | ชื่อหน้า และปุ่มที่ทำกับทั้งหน้า (ส่งออกสรุป · ส่งออกรายชื่อ · บันทึกเป็น PDF) ชิดขวา |
| กลาง | ขอบเขตที่กำลังดู แล้วบรรทัดถัดมาเป็นยอดผู้ป่วยของขอบเขตนั้น |
| ล่าง | ตัวกรองทั้งเจ็ดช่องเรียงแถวเดียวใต้เส้นคั่น |

เดิมตัวกรองอยู่ข้างชื่อหน้าในตารางสี่คอลัมน์ตายตัว พอเพิ่มจากสามช่องเป็นเจ็ดช่อง
จึงตกเป็นสองแถวไม่เท่ากัน มีปุ่มล้างค้างอยู่กลางแถวแรก และเหลือช่องว่างก้อนใหญ่
ข้างชื่อหน้า ย้ายลงมาเป็นแถวเต็มความกว้างแล้วเอาปุ่มส่งออกขึ้นไปแทนที่ช่องว่างนั้น

ทั้งเจ็ดช่องใช้ `flex-basis: 0` แบ่งความกว้างเท่า ๆ กัน ไม่ได้จองความกว้างตั้งต้นไว้
ถ้าจองไว้ ผลรวมจะเกินแถวจนดันปุ่มล้างตกไปอยู่บรรทัดใหม่ตัวเดียวโดด ๆ

**บรรทัดขอบเขต** ใส่ทุกตัวกรองที่เปิดใช้อยู่ ไม่ใช่แค่พื้นที่กับช่วงเวลา เช่น
"จังหวัดกระบี่ · อ.เมืองกระบี่ · ปีงบ 2569 ไตรมาส 2 · จบแล้ว · Dx stroke"
เพราะตอนพิมพ์ลงกระดาษดรอปดาวน์ถูกซ่อนหมด ถ้าบรรทัดนี้ไม่บอก เอกสารที่ส่งต่อกันไป
จะไม่มีอะไรบอกเลยว่าเลขในนั้นกรองอะไรไว้บ้าง

### ตัวกรอง

พื้นที่ · อำเภอ · ตำบล · ปีงบ · ไตรมาส · สถานะ · กลุ่มการวินิจฉัย
ทุกช่องมีผลกับทั้งหน้าพร้อมกัน ไม่ใช่แค่หัวเรื่อง ตัวเลือกในดรอปดาวน์คิดจากผู้ป่วย
ทุกคนก่อนกรอง ตัวเลือกจึงไม่หายไปตอนเปลี่ยนตัวกรองอื่น

ปุ่ม **ล้างตัวกรอง** ท้ายแถวล้างทุกช่อง ต่างจากปุ่ม **ล้าง** บนแดชบอร์ดที่ล้างเฉพาะพื้นที่
เพราะหน้านี้มีเจ็ดช่อง ปุ่มที่ล้างแค่สามช่องแรกจะหลอกให้คิดว่าล้างหมดแล้ว
ปุ่มกดไม่ได้เมื่อยังไม่ได้กรองอะไร

ปีงบกับไตรมาสคัดผู้ป่วยจาก `start_date` ฐานเดียวกับกราฟผู้ป่วยเข้าใหม่บนแดชบอร์ด
คือ "ผู้ป่วยที่**เริ่ม**โปรแกรมในปีงบนั้น" ไม่ใช่ "ที่จบในปีงบนั้น"
ตรงกับวิธีนับของรายงาน IMC ที่ส่งเขต ป้ายในช่องเขียนกำกับว่า "นับจากวัน Start" ไว้กันเข้าใจผิด
เลือกไตรมาสได้ต่อเมื่อเจาะปีงบไว้แล้ว เปลี่ยนปีงบจะล้างไตรมาสให้เอง
ป้ายในดรอปดาวน์กำกับเดือนไว้ เช่น ไตรมาส 1 (ต.ค.-ธ.ค.) เพราะไตรมาสงบประมาณ
ไม่ตรงกับไตรมาสปฏิทิน คนที่ชินแบบเดิมจะได้ไม่เลือกผิด

**สถานะ** แยกเคสที่ยังดูแลอยู่ออกจากเคสที่จบแล้ว ถ้าไม่มีช่องนี้ ทั้งสองกลุ่มจะปนกัน
ในทุกแท่ง แล้วอ่านไม่ออกว่ากลุ่ม ADL ที่เห็นเป็นภาพของคนที่ยังดูแลอยู่ หรือรวมคนที่จบไปแล้ว

### ตัวชี้วัดผลลัพธ์

แผง **ผลลัพธ์การดูแล** บนสุด ห้าตัวเลขในการ์ดใบเดียว คิดจากข้อมูลที่มีอยู่แล้วในชีต
ไม่ต้องกรอกอะไรเพิ่ม

| ตัวเลข | คิดจาก | ฐาน |
|---|---|---|
| BI เพิ่มเฉลี่ย | `latest_bi` ลบ `first_bi` | รายที่มีคะแนนทั้งสองครั้ง |
| เลื่อนกลุ่ม ADL ดีขึ้น | กลุ่มของใบประเมินใบแรกเทียบใบล่าสุด | รายที่มีใบประเมินลงวันที่แล้ว **สองใบขึ้นไป** |
| อยู่ในโปรแกรมครบ 6 เดือน | `end_date` ลบ `start_date` เทียบ `CONFIG.IMC_DURATION_DAYS` | เคสที่ปิดแล้วและมีวันครบทั้งสองด้าน |
| วันรอเข้าโปรแกรม | `start_date` ลบ `dc_date` | รายที่มีวันครบทั้งสองด้าน |
| ครั้งที่ได้ PT | `pt_visit_count` | รายที่มีตัวเลขในช่องนี้ |

**เลื่อนกลุ่ม ADL** ต้องมีใบประเมินสองใบขึ้นไปจึงเข้าฐาน มีใบเดียวแปลว่ายังไม่มีอะไร
ให้เทียบ ถ้านับรวมจะไปกองอยู่ในช่อง "คงที่" แล้วทำให้ดูเหมือนดูแลไปก็ไม่มีอะไรเปลี่ยน
ทั้งที่ยังไม่ได้วัดซ้ำเลย

**อยู่ครบ 6 เดือน** นับจากวันจริงที่เริ่มถึงวันจริงที่จบ ไม่ได้อ่านช่อง `six_month_status`
เพราะช่องนั้นเก็บผลตอนกดบันทึกครั้งสุดท้าย พอเวลาผ่านไปก็ค้างอยู่ที่ค่าเดิม

**วันรอเข้าโปรแกรม** กับ **ครั้งที่ได้ PT** แสดงค่ากลางเป็นตัวเลขหลักและมีค่าเฉลี่ยกำกับ
เพราะข้อมูลไม่กี่สิบราย รายที่รอนานผิดปกติรายเดียวดันค่าเฉลี่ยได้มาก แต่ไม่ขยับค่ากลาง

ค่าที่ยังคิดไม่ได้ขึ้นขีด `—` ไม่ใช่เลขศูนย์ ซึ่งอ่านเหมือนวัดแล้วได้ศูนย์

**ตัวเลขที่มาจากคนไม่กี่ราย** ทำให้จางลงและติดป้าย **ข้อมูลยังน้อย** เกณฑ์อยู่ที่
`thinBase()` คือฐานน้อยกว่า 5 ราย หรือครอบคลุมกลุ่มที่ควรตอบได้ไม่ถึงหนึ่งในสาม
ดูสัดส่วนด้วยไม่ใช่ดูแค่จำนวน เพราะฐานสิบจากร้อยก็ยังพูดแทนทั้งกลุ่มไม่ได้
และแต่ละตัวเทียบกับกลุ่มของตัวเอง "อยู่ครบ 6 เดือน" เทียบกับเคสที่จบแล้ว
ที่เหลือเทียบกับผู้ป่วยทั้งกลุ่ม

เจอตอนใช้ข้อมูลจริง 59 ราย หน้าจอขึ้น "อยู่ครบ 6 เดือน 50%" ตัวโตเท่ากับตัวอื่น
ทั้งที่มาจากสองราย จากเคสที่จบแล้ว 32 ราย ฐานเขียนไว้แล้วแต่เป็นตัวเล็กสีเทา
คนที่กวาดตาผ่านจะอ่านว่าครึ่งหนึ่งอยู่ครบ ทั้งที่จริงคือมีเคสที่ตอบได้แค่สองราย
ไม่ซ่อนตัวเลขทิ้ง เพราะสองรายก็ยังเป็นข้อมูล แค่ต้องไม่อ่านเป็นภาพของทั้งกลุ่ม

**ยอดผู้ป่วยไม่อยู่ในแผงนี้** เพราะไม่ใช่ผลลัพธ์ แต่เป็นขอบเขตของตัวเลขทุกตัว
จึงไปอยู่บนหัวหน้าชั้นกลาง เป็นบรรทัดของตัวเองต่อจากบรรทัดขอบเขต
"ผู้ป่วย 59 ราย · กำลังดูแล 27 · จบแล้ว 32 · ประเมิน BI แล้ว 59 ราย"

### ทำไมไม่ใช้การ์ดสีแบบแดชบอร์ด

แผงนี้ใช้หน้าตาเดียวกับการ์ดอื่นบนหน้ารายงาน คือการ์ดขาว หัวข้อมีไอคอนเขียวน้ำทะเล
และมีบรรทัดบอกฐานใต้หัวข้อ ทั้งที่มี `statCard()` ของแดชบอร์ดให้หยิบมาใช้ได้เลย
ตั้งใจไม่ใช้ด้วยสองเหตุผล

**หนึ่ง** สองหน้าตอบคนละคำถาม ถ้าหน้าตาเหมือนกันคนอ่านจะนึกว่าเปิดแดชบอร์ดอยู่
ยิ่งใบ "คะแนน BI เพิ่มเฉลี่ย" มีอยู่บนแดชบอร์ดด้วย คนละฐานคนละช่วงเวลาแต่ป้ายเดียวกัน
ถ้าวางเป็นการ์ดสีเหมือนกันอีกจะแยกไม่ออกว่ากำลังอ่านเลขของหน้าไหน

**สอง** หน้านี้ใช้เฉดเขียวน้ำทะเลไล่เข้ม-อ่อนสื่อระดับการพึ่งพาในแท่ง ADL อยู่แล้ว
การเติมพาสเทลสี่สีที่ไม่ได้แปลว่าอะไรเข้ามา ทำให้สีบนหน้าเดียวกันมีความหมายสองระบบ
พอเหลือระบบเดียว สีบนหน้านี้จึงแปลว่าความรุนแรงเสมอ และตอนพิมพ์ก็ไม่เปลืองหมึก
กับพื้นสีที่ไม่ได้สื่ออะไร

เทสต์ใน `tests/test-area-browser.js` คุมไว้ว่าหน้ารายงานต้องไม่มี `.stat-card` อยู่เลย

### ทุกการ์ดบอกฐานของตัวเอง

การ์ดแท่งหกใบใช้ฐานไม่เท่ากัน หัวการ์ดทุกใบจึงเขียนกำกับว่า "จาก N ราย..."

| การ์ด | ฐาน |
|---|---|
| การกระจายคะแนน BI ล่าสุด | รายที่มีคะแนน BI |
| กลุ่ม ADL จากผลประเมินล่าสุด | รายที่ประเมินแล้ว |
| กลุ่มการวินิจฉัย · หอผู้ป่วย · รูปแบบโปรแกรม | ผู้ป่วยทั้งหมด |
| เหตุจบโปรแกรม | รายที่จบแล้ว |

เดิมเขียนกำกับแค่ใบเหตุจบใบเดียว ตอนที่ยังไม่มีใครค้างประเมิน ตัวเลขทุกใบบังเอิญ
เท่ากันหมดจนไม่มีใครสังเกต พอมีคนที่ยังไม่ประเมินเมื่อไหร่ เปอร์เซ็นต์จะอ่านเทียบ
ข้ามการ์ดไม่ได้ทันทีโดยไม่มีอะไรเตือน

**เหตุจบโปรแกรม** นับจาก `dc_reason` ซึ่งเป็นช่องบังคับกรอกตอนปิดเคส และเลือกจาก
รายการตายตัว 8 แบบใน `CONFIG.DC_REASON` จึงจัดกลุ่มได้โดยไม่ต้องเดา เคสที่ยังไม่ปิด
ไม่ถูกนับเลย ไม่ใช่ถูกนับเป็น "ไม่ระบุ" เพราะยังไม่ถึงเวลาที่ต้องกรอก

### กดแท่งแล้วเห็นว่าใคร

ทุกแท่ง ทุกแถวในตารางแจกแจงพื้นที่ และทุกบรรทัดในกล่องข้อมูลไม่ครบ กดแล้วเปิด
รายชื่อผู้ป่วยที่อยู่เบื้องหลังตัวเลขนั้นได้ เปิดเวชระเบียนต่อหรือส่งออก CSV ก็ได้

ทำได้เพราะ `apiReport()` ติดกลุ่มที่ใช้นับไว้กับผู้ป่วยแต่ละรายใน `groups` ตั้งแต่ต้น
แล้วทั้งตัวเลขบนแท่ง ฐานของการ์ด และรายชื่อที่กดดู อ่านจากที่นั่นที่เดียวกันหมด
ตัวเลขกับรายชื่อจึงไม่มีทางเพี้ยนจากกัน วิธีเดียวกับที่กล่อง "ต้องจัดการ" บนแดชบอร์ดใช้อยู่
แท่งที่ยอดเป็นศูนย์ไม่ใช่ปุ่ม เพราะกดแล้วได้แต่กล่องรายชื่อเปล่า

กลุ่มที่มีเกิน 6 กลุ่มจะยุบหางเหลือ 5 อันดับแรก แล้วรวมที่เหลือเป็นแถวเดียวว่า
"อื่น ๆ อีก N กลุ่ม" พร้อมยอดรวม กดกางดูทั้งหมดได้ หางยาวที่แต่ละกลุ่มมีรายเดียว
กินที่ครึ่งการ์ดโดยไม่ได้ข้อมูลเพิ่ม ส่วน "ไม่ระบุ" ถูกดันไว้ล่างสุดเสมอไม่ว่าจะมีกี่ราย
เพราะไม่ใช่กลุ่มจริง ถ้าเรียงตามจำนวนล้วนมันจะไปแทรกกลางกลุ่มที่มีความหมาย

### ข้อมูลที่ยังกรอกไม่ครบ

ช่องที่ว่างจะไปโผล่เป็น "ไม่ระบุ" กระจายอยู่ในหลายการ์ด หรือทำให้ฐานของการ์ดผลลัพธ์
หดจนตัวเลขพูดแทนกลุ่มไม่ได้ กล่องนี้รวมมาไว้ที่เดียว จึงเห็นขนาดของปัญหาจริง
และกดเข้าไปแก้ได้ ไม่มีอะไรค้างก็ไม่แสดงกล่องเลย ตรวจสิบข้อ

| ช่อง | ทำให้อะไรเพี้ยน |
|---|---|
| พื้นที่ · การวินิจฉัย · หอผู้ป่วย · รูปแบบโปรแกรม | โผล่เป็น "ไม่ระบุ" ในการ์ดแท่ง |
| วัน Start | หลุดจากตัวกรองปีงบและไตรมาส |
| ยังไม่เคยประเมิน BI | หลุดจากการ์ดกลุ่ม ADL |
| **วันสิ้นสุดของเคสที่ปิดแล้ว** | ฐานของ "อยู่ครบ 6 เดือน" หด |
| **วันจำหน่ายจากหอผู้ป่วย (D/C)** | ฐานของ "วันรอเข้าโปรแกรม" หด |
| **จำนวนครั้งที่ได้ PT** | ฐานของ "ครั้งที่ได้ PT" หด |
| เหตุจบของเคสที่ปิดแล้ว | โผล่เป็น "ไม่ระบุ" ในการ์ดเหตุจบ |

สามข้อตัวหนาเพิ่มมาทีหลัง หลังพบว่าข้อมูลจริง 59 รายทำให้ "อยู่ครบ 6 เดือน"
เหลือฐานสองรายจากที่จบแล้ว 32 ราย โดยไม่มีอะไรบอกว่าอีกสามสิบรายหายไปไหน

ช่อง **จำนวนครั้งที่ได้ PT** ระบบนับให้เองจากบันทึกการติดตามที่ประเภทเป็น PT
ว่างแปลว่ายังไม่เคยมีใครบันทึกการติดตามให้รายนั้น ไม่ได้แปลว่าผู้ป่วยไม่ได้ PT
ป้ายจึงเขียนว่า "ยังไม่มีบันทึก" ไม่ใช่ "ไม่ได้ PT"

แยกจากกล่อง "ต้องจัดการ" บนแดชบอร์ดเพราะตอบคนละคำถาม กล่องนั้นถามว่าต้องไป
ทำอะไรกับผู้ป่วย ส่วนกล่องนี้ถามว่าตัวเลขในรายงานเชื่อได้แค่ไหน

### แจกแจงรายพื้นที่

ตารางเทียบพื้นที่กับกลุ่ม ADL ในตารางเดียว ตอบคำถามที่แท่งเดี่ยว ๆ ตอบไม่ได้
คือพื้นที่ไหนผู้ป่วยหนักกว่ากัน เจาะอำเภอไว้แล้วตารางจะแตกต่อเป็นรายตำบลของอำเภอนั้นเอง
แถวที่ไม่มีผู้ป่วยถูกตัดออก ตารางจะได้ไม่ยาวลอย

### ความคืบหน้ารายบุคคล

แสดง 10 อันดับแรกก่อน กด **ดูทั้งหมด** ได้ และสลับทิศเรียงได้ด้วยปุ่ม
**ดูรายที่แย่ลงก่อน** แถวที่คะแนนไม่เพิ่มขึ้น (ผลต่าง ≤ 0) มีแถบสีกำกับหัวแถว
เดิมเรียงจากคะแนนเพิ่มมากสุดทางเดียว คนที่คะแนนลดลงจึงไปกองอยู่ท้ายตาราง
ทั้งที่เป็นกลุ่มที่ต้องดูที่สุด และตารางไม่จำกัดจำนวนแถว พอผู้ป่วยโตเป็นหลายร้อยราย
หน้าจะยาวจนเลื่อนหาอะไรไม่เจอ

### ส่งออกและพิมพ์

| ปุ่ม | ได้อะไร |
|---|---|
| ส่งออกตารางสรุป | ตัวกรองที่ใช้ · ตัวชี้วัดผลลัพธ์ทุกตัวพร้อมฐาน · ทุกแท่งพร้อมจำนวนและร้อยละ · ตารางรายพื้นที่ · ข้อมูลที่ยังไม่ครบ |
| ส่งออกรายชื่อ | ผู้ป่วยทุกรายในตัวกรอง คอลัมน์ชุดเดียวกับที่ส่งออกจากหน้ารายชื่อ |
| ส่งออก (ในตารางความคืบหน้า) | เฉพาะรายที่ประเมินครบสองครั้ง พร้อมคะแนนแรกรับ ล่าสุด และผลต่าง |

ไฟล์สรุปเขียนตัวกรองไว้บนหัวไฟล์ด้วย เพราะไฟล์ที่ส่งต่อกันไปจะถูกเปิดอ่านโดยคนที่ไม่ได้
นั่งเลือกตัวกรองเอง ถ้ามีแต่ตัวเลขลอย ๆ จะบอกไม่ได้ว่าเป็นเลขของพื้นที่ไหนปีไหน
ทุกไฟล์เป็น CSV ที่นำหน้าด้วย BOM ไม่งั้น Excel บนวินโดวส์อ่านภาษาไทยเป็นตัวขยะ

ปุ่ม PDF บนแถบบนพิมพ์หน้าที่กำลังดูอยู่ ถ้าอยู่หน้าแดชบอร์ดหรือหน้ารายงานก็พิมพ์หน้านั้น
หน้าอื่นเป็นฟอร์มกับรายชื่อซึ่งพิมพ์แล้วไม่ได้ใช้ จึงพากลับไปแดชบอร์ดแทน
ตอนพิมพ์ กล่องตัวกรองกับปุ่มส่งออกถูกซ่อนทั้งกล่อง ส่วนพื้นที่ ช่วงเวลา และตัวกรองอื่น
ที่เลือกอยู่ เขียนไว้ใต้หัวเรื่องแล้ว จึงไม่มีอะไรหายไปจากกระดาษ

### กระดาษ A4 แนวตั้ง

`@page` ตั้งเป็น A4 แนวตั้ง ตรงกับแนวที่แฟ้มเอกสารของหน่วยงานใช้และถ่ายเอกสารต่อได้
โดยไม่ต้องหมุน หักขอบแล้วเหลือความกว้างที่พิมพ์ได้จริงราว 725px
ตัวเลขทุกตัวในบล็อก `@media print` ตั้งมาจากความกว้างนั้น

**725px ต่ำกว่าเบรกพอยต์มือถือ 900px** กฎของมือถือจึงติดไปบนกระดาษด้วย
ซึ่งเคยทำให้ตารางถูกพับเป็นการ์ดเรียงลงมาทีละคน ผู้ป่วยหนึ่งรายกินห้าบรรทัด
และเอกสารบานจากสองแผ่นเป็นห้าแผ่น บล็อก `@media print` จึงดึงตารางกลับมาเป็น
ตารางจริง และแก้กฎมือถืออื่นที่ไม่เข้ากับกระดาษ เช่นการ์ดสถิติที่ให้ใบสุดท้ายกินสองช่อง

**การ์ดแท่งบนกระดาษวางด้วย `column-count` ไม่ใช่ grid** เพราะ Chrome แบ่ง grid
ข้ามหน้ากระดาษไม่เป็น ทั้งตารางจะถูกยกไปทั้งก้อนแล้วเหลือครึ่งหน้าว่างไว้ข้างหลัง
ดันของที่เหลือไปเรื่อย ๆ จนเอกสารบานเป็นหกแผ่น

### หัวกระดาษของหน่วยงาน

เอกสารที่พิมพ์ออกมามีหัวกระดาษกับท้ายกระดาษของหน่วยงานเอง

| | มีอะไร |
|---|---|
| หัวกระดาษ | เครื่องหมายของระบบ · **โรงพยาบาลกระบี่** · กลุ่มงานเวชกรรมฟื้นฟู · ชื่อระบบและวันที่พิมพ์ชิดขวา · คั่นด้วยเส้นสีแบรนด์ |
| ท้ายกระดาษ | ชื่อหน่วยงาน และ "จัดทำโดยระบบ Intermediate Care · วันที่" |

ทั้งสองอย่างอยู่ใน `index.html` นอก `<main>` เพราะ `main` ถูกเขียนทับใหม่ทุกครั้งที่เปลี่ยนหน้า
วางไว้ข้างนอกจึงติดไปกับทุกหน้าที่พิมพ์ได้ โดยไม่ต้องให้แต่ละหน้าวาดเอง
บนจอทั้งคู่ถูกซ่อน เพราะมีแถบบนกับเมนูซ้ายบอกอยู่แล้ว

ชื่อหน่วยงานกับวันที่เติมด้วย `fillPrintHeader()` ทั้งตอนบูตและตอน `beforeprint`
ผูกกับอีเวนต์อย่างเดียวไม่พอ เพราะการสั่งพิมพ์บางทางไม่ยิงอีเวนต์นี้
แล้วหัวกระดาษจะออกมาเป็นช่องว่างโดยไม่มีใครรู้

**ขอบกระดาษต้องอยู่ที่ `@page` ไม่ใช่ `padding` ของเนื้อหา** เคยตั้งขอบเป็นศูนย์แล้วไป
เว้นระยะที่ `.content` แทน เพื่อไม่ให้เบราว์เซอร์มีที่วาดหัว-ท้ายของตัวเอง
แต่ `padding` มีผลครั้งเดียวตอนต้นเอกสาร แผ่นที่สองเป็นต้นไปจึงเริ่มชิดขอบกระดาษพอดี
ขอบของ `@page` มีผลกับทุกแผ่น จึงเป็นที่เดียวที่ตั้งได้ถูกต้อง

### เลขหน้า

เขียนเองใน `@bottom-center` ของ `@page` ไม่ได้พึ่งท้ายกระดาษของเบราว์เซอร์
ซึ่งพ่วงพาธ `file:///` มาด้วยและย้ายที่ไม่ได้

```css
@page {
  margin: 12mm 9mm 13mm;
  @bottom-center { content: "หน้า " counter(page) " / " counter(pages); }
}
```

เคยเข้าใจว่า Chrome ไม่รองรับ margin box ของ CSS จึงเขียนเลขหน้าเองไม่ได้
ทดสอบแล้วพบว่ารองรับ วิธีทดสอบคือทำหน้าจำลองที่มีแต่กล่องสีเทา ไม่มีตัวหนังสือเลย
แล้วสั่งพิมพ์เป็น PDF สองรอบ ไม่ใส่กฎได้ 0 ฟอนต์ ใส่แล้วได้ 3 ฟอนต์บนเอกสาร 3 แผ่น
คือหน้าละหนึ่ง เทสต์ในชุดทดสอบทำแบบเดียวกันกับเอกสารจริง โดยปิดกฎด้วย `content: none`
แล้วเทียบจำนวนก้อนข้อความในไฟล์ที่ได้

**หัว-ท้ายของเบราว์เซอร์ยังต้องปิดเองครั้งเดียว** ที่ช่อง **หัวกระดาษและท้ายกระดาษ**
ในกล่องพิมพ์ของ Chrome ซึ่งจำค่าไว้ให้ครั้งถัดไป กฎ `@top-left { content: "" }` และพวก
ใส่ไว้แล้วเผื่อเบราว์เซอร์รุ่นที่ยอมให้ CSS แทนที่ของตัวเอง แต่ยืนยันไม่ได้จาก
`Page.printToPDF` เพราะโหมด headless ไม่วาดหัว-ท้ายให้ไม่ว่าจะสั่ง `displayHeaderFooter`
อย่างไร ต้องเปิดกล่องพิมพ์ดูด้วยตา

### ชื่อเอกสารและชื่อไฟล์

`fillPrintHeader()` ตั้ง `document.title` เป็น **"รายงาน IMC - โรงพยาบาลกระบี่ - 7 ก.ย. 2569"**
ตามหน้าที่กำลังพิมพ์ ซึ่งเบราว์เซอร์ใช้สองที่พร้อมกัน

- เป็นชื่อไฟล์ตั้งต้นตอนกด **บันทึกเป็น PDF** เดิมไม่ได้ตั้งไว้เลย จึงได้ไฟล์ชื่อ `index.html`
- เป็นข้อความบนหัวกระดาษที่เบราว์เซอร์วาดให้ ถ้ายังเปิดหัว-ท้ายไว้

เว้นอักขระที่ตั้งชื่อไฟล์บนวินโดวส์ไม่ได้ โดยเฉพาะขีดทับใน "รายงาน / BI" ซึ่งเป็นชื่อหน้าจริง
บนหน้าจอ ใช้ขีดกลางคั่นแทน ชื่อที่ได้จึงบันทึกลงเครื่องได้ทันทีโดยไม่ต้องแก้

### การ์ดต้องไม่ถูกผ่ากลาง

`tr, .panel, .outcome-fig { break-inside: avoid; }` ที่เหลือไม่พอก็ยกไปขึ้นแผ่นใหม่ทั้งใบ
ไม่สั่งที่ตัวตาราง เพราะตารางที่ยาวเกินหนึ่งแผ่นควรแบ่งได้ตามปกติโดยมีหัวตารางซ้ำให้
(`thead { display: table-header-group }`) ดีกว่าถูกยกทั้งก้อนแล้ว Chrome ค่อยยอมแพ้แบ่งเองทีหลัง

เคยสงสัยว่า Chrome ทำตาม `break-inside: avoid` จริงไหม จึงทดสอบด้วยหน้าจำลอง
วางกล่องสูง 130px คร่อมเส้นแบ่งหน้า แล้วอ่านความสูงของสี่เหลี่ยมที่วาดจริงในไฟล์ PDF
ไม่ใส่ `avoid` กล่องถูกผ่าเป็น 86 กับ 44 ใส่แล้วย้ายไปทั้งใบ 130 — ทำตามจริง

`tests/test-area-browser.js` สั่ง `Page.printToPDF` จริงแล้วอ่านจากไฟล์ที่ได้
ไม่ใช่เดาจากความสูงบนจอ ตรวจแนวกระดาษ นับจำนวนแผ่น (ข้อมูลตัวอย่างหกรายต้องไม่เกิน
สามแผ่น) ตรวจว่าเลขหน้าถูกวาดจริง ตรวจว่า `document.title` ตั้งชื่อไฟล์ได้
แล้วตรวจซ้ำที่ความกว้าง 725px ว่าไม่มีอะไรล้นทั้งหน้ารายงานและแดชบอร์ด

### เทียบงวดก่อน

เลือกปีงบหรือไตรมาสไว้แล้ว ท้ายแผงผลลัพธ์จะมีบรรทัดปิดท้ายบอกตัวเลขจริงของงวดก่อน
เช่น "เทียบกับปีงบ 2568 · ผู้ป่วย 41 ราย · BI เพิ่มเฉลี่ย +2.7" คิดด้วยตัวกรองชุดเดียวกัน
ทุกช่อง ไม่งั้นเลขที่เอามาเทียบจะเป็นคนละกลุ่มผู้ป่วย ไม่เลือกงวดก็ไม่มีบรรทัดนี้
เพราะ "ทุกปีงบ" ไม่มีงวดก่อนหน้าให้เทียบ

บอกตัวเลขจริงไม่ใช่แค่ส่วนต่าง เพราะ "+0.8" บอกไม่ได้ว่าฐานที่เทียบมามีคนกี่ราย
งวดที่มีคนสามรายกับสามสิบรายเลื่อนขึ้นเท่ากันไม่ได้แปลว่าเรื่องเดียวกัน

ส่วนต่างของคะแนน BI มีป้ายเล็กใต้ตัวเลขนั้นด้วย แต่ขึ้นเฉพาะตอนที่งวดก่อนมีคะแนน
ให้เทียบจริง งวดก่อนที่ไม่มีใครประเมินเลยไม่ใช่ศูนย์ที่เอามาลบได้ ถ้าโชว์ "+3.5"
จะอ่านเหมือนดีขึ้นจากศูนย์

## หน้าการติดตาม

หน้านี้มีสองงานที่ต่างกันวางอยู่ด้วยกัน แยกกันชัด ๆ เพราะทำคนละเวลา

**ด้านบน — ถึงกำหนดต้องตาม** คือสิ่งที่ต้องลงมือวันนี้ คัดจากผู้ป่วยที่ยังไม่ปิดเคส
และมีวันนัด OPD (`kbh_appt_date`) ที่เลยมาแล้วหรือจะถึงภายใน `CONFIG.FU_DUE_AHEAD_DAYS`
(ตั้งไว้ 7 วัน) เรียงจากเลยนัดนานที่สุดลงมา แต่ละแถวบอกด้วยว่าตามครั้งล่าสุดเมื่อไร
จะได้แยกออกว่ารายไหนตามไปแล้วแต่ลืมเลื่อนนัด กับรายไหนที่ยังไม่มีใครแตะเลย
ปุ่มปฏิทินท้ายแถวพาไปฟอร์มบันทึกของรายนั้นตรง ๆ กดที่ชื่อเปิดเวชระเบียนตามปกติ

ใช้ช่องวันนัดช่องเดียวกับที่แดชบอร์ดและธงงานค้าง **เลยกำหนดนัดแล้ว** ใช้
ทั้งสามที่จึงพูดถึงนัดเดียวกันเสมอ ไม่มีหน้าไหนตีความคำว่า "ถึงกำหนด" เป็นของตัวเอง

**ด้านล่าง — สมุดบันทึก** คือรายการที่ตามไปแล้วทั้งหมด ค้นด้วย HN ชื่อ
หรือข้อความในบันทึกก็ได้ กรองตามประเภท (PT / เยี่ยมบ้าน / OPD / โทรติดตาม)
และตามช่วงเวลาได้ ส่งมาทุกแถว ไม่ตัดที่ 60 รายการล่าสุดอย่างที่เคยเป็น
ซึ่งทำให้ของเก่าหายไปเงียบ ๆ โดยคนเปิดดูเข้าใจว่าเห็นครบแล้ว

### รายการที่ยังไม่มีวันที่

ตอนนำเข้าข้อมูลเดิม ช่องติดตามที่อ่านวันที่ไม่ออก (เช่น `ยบ.IMC 11/11` ที่ไม่มีปีกำกับ)
จะถูกเก็บข้อความไว้โดยเว้นวันที่ให้คนมาเติมเอง แถวเหล่านี้เคยถูกกรองทิ้งตั้งแต่ฝั่งเซิร์ฟเวอร์
กองงานที่ต้องไล่เติมมากที่สุดจึงเป็นกองเดียวที่มองไม่เห็นจากหน้าการติดตาม

ตอนนี้แสดงอยู่ในตาราง ติดป้ายสีส้มว่า **ยังไม่มีวันที่** ไว้ในช่องวันที่ อยู่ท้ายรายการเสมอ
เลือกดูเฉพาะกลุ่มนี้ได้จากตัวกรองช่วงเวลา และจำนวนที่ค้างอยู่เขียนไว้ใต้หัวเรื่องด้วย

### บันทึกการติดตามจากหน้านี้

ปุ่ม **+ บันทึกการติดตาม** ยืมหน้ารายชื่อมาเป็นตัวเลือกผู้ป่วย แทนที่จะสร้างรายการ
ให้เลือกขึ้นมาใหม่ เพราะที่นั่นมีทั้งช่องค้นหาและตัวกรองอยู่แล้ว คนที่นึกชื่อไม่ออก
จะได้ค้นด้วย HN หรือกรองตาม Ward ได้ ระหว่างอยู่ในโหมดนี้จะมีแถบบอกไว้พร้อมปุ่มยกเลิก
กดที่ชื่อแล้วเข้าฟอร์มบันทึกของรายนั้นเลย

โหมดเลือกติดมากับการเรียกหน้า (`go('list', { pick: 'fu' })`) ไม่ได้ค้างไว้เป็นสถานะ
กดเมนูรายชื่อตามปกติจึงหลุดออกจากโหมดเอง

### นัดครั้งถัดไป

ฟอร์มบันทึกรายการใหม่มีช่อง **นัดครั้งถัดไป** กรอกแล้วระบบเลื่อนวันนัด OPD
ของผู้ป่วยรายนั้นให้เลย ปล่อยว่างไว้แปลว่าไม่เปลี่ยนวันนัดเดิม

เดิมตามคนไข้เสร็จแล้ววันนัดยังค้างอยู่ที่เดิม ธง **เลยกำหนดนัดแล้ว** จึงไม่มีวันหายไปเอง
จนกว่าจะมีคนเข้าไปแก้เวชระเบียนแยกอีกที งานที่ทำไปแล้วเลยยังค้างอยู่ในระบบ

ช่องนี้มีเฉพาะตอนบันทึกรายการใหม่ การแก้บันทึกเก่าไม่ควรไปขยับวันนัดที่ใช้อยู่

### เลข "ครั้งที่" นับตามวันที่ ไม่ใช่ลำดับที่กด

ทุกครั้งที่บันทึก ระบบไล่เลขครั้งที่ของผู้ป่วยรายนั้นใหม่ตามวันที่จริง
(เขียนเฉพาะแถวที่เลขเปลี่ยน และเขียนแค่ช่องเดียว) รายการที่ยังไม่มีวันที่ไปต่อท้ายเสมอ

เดิมเลขครั้งที่คือลำดับที่กดบันทึก พอกรอกย้อนหลัง เช่น นึกได้ว่าลืมลงเยี่ยมบ้านของเดือนก่อน
รายการนั้นจะกลายเป็นครั้งที่ 5 ที่วันที่เก่ากว่าครั้งที่ 4 แล้วไทม์ไลน์เรียงสลับกัน
โดยไม่มีอะไรบอก ข้อมูลเก่าที่บันทึกไว้ก่อนหน้านี้ซ่อมได้ด้วยเมนู **ติดตั้งระบบ**
ซึ่งไล่เลขให้ทั้งชีตในครั้งเดียว และบอกจำนวนแถวที่แก้ไปในกล่องสรุป

## แก้ไขผลประเมินและบันทึกการติดตามที่บันทึกไปแล้ว

ในหน้าเวชระเบียน ทุกแถวของตารางคะแนน BI และทุกรายการในไทม์ไลน์การติดตาม
มีปุ่มดินสอสำหรับแก้ไข กดแล้วเปิดฟอร์มเดิมพร้อมค่าที่บันทึกไว้

หลังบ้านรองรับการแก้ไขมาตั้งแต่ต้น `apiSaveBi` กับ `apiSaveFollowup` มองหา
`assess_id` / `fu_id` ที่ส่งมา ถ้าเจอของเดิมก็เขียนทับและรักษา `created_at` ไว้
สิ่งที่ขาดคือหน้าจอไม่เคยส่งรหัสกลับไป ทุกครั้งจึงกลายเป็นการเพิ่มรายการใหม่
ตอนนี้ฟอร์มส่ง `assess_id` / `fu_id` เดิมกลับไปด้วย ฟอร์ม BI ส่ง `seq` เดิมไปด้วย
ส่วนฟอร์มติดตามไม่ต้องส่ง เพราะเซิร์ฟเวอร์ไล่เลขครั้งที่เองจากวันที่ทุกครั้งที่บันทึก

ปุ่มดินสอมีในหน้าการติดตามด้วย ฟอร์มจึงต้องโหลดเวชระเบียนของรายนั้นให้ครบก่อนวาด
เดิมอ่านจากของที่โหลดไว้แล้วอย่างเดียว ถ้าเข้ามาจากหน้าที่ยังไม่เคยเปิดเวชระเบียนรายนั้น
จะได้ค่าว่างแล้วกลายเป็นบันทึกรายการใหม่ซ้ำขึ้นมาอีกอันโดยไม่มีอะไรเตือน

**ข้อควรรู้:** ผลประเมินที่นำเข้าจากไฟล์เดิมมีแต่คะแนนรวม ไม่มีคะแนนราย 10 ข้อ
กดแก้ไขแล้วช่องจะว่างทั้งหมดและบันทึกไม่ได้จนกว่าจะเลือกครบ ฟอร์มจึงขึ้นแถบเตือน
บอกไว้ตั้งแต่ต้นพร้อมคะแนนรวมเดิม ถ้ายังไม่พร้อมกรอกใหม่ให้กดย้อนกลับ ของเดิมไม่ถูกแตะ

## ประเมิน BI ต่อจากบันทึกการติดตาม

ฟอร์มบันทึกการติดตามรายการใหม่มีติ๊ก **ประเมิน BI ต่อหลังบันทึก**
กดบันทึกแล้วระบบพาไปหน้าประเมินโดยเติมวันที่ของการติดตามให้เลย
มาตรวจครั้งเดียวจึงกรอกต่อกันได้โดยไม่ต้องย้อนกลับไปหาปุ่มเอง

ตั้งใจไม่ยุบสองอย่างนี้เป็นฟอร์มเดียว เพราะจำนวนครั้งไม่เท่ากัน ผู้ป่วยหนึ่งคน
ติดตามสิบครั้งแต่ประเมิน BI สามครั้งเป็นเรื่องปกติ และตัวเลขทั้งระบบ
(`bi_1..bi_5` กราฟ กลุ่ม ADL งานค้างเรื่องประเมินเกิน 8 สัปดาห์) นับจาก
`bi_assessments` ทั้งหมด การยุบตารางจะกระทบทุกจุดโดยได้ผลตอบแทนน้อย

## เกณฑ์ที่ระบบคำนวณให้

- **คะแนน Barthel Index** รวม 10 ข้อ เต็ม 20 คะแนน คิดสดขณะกรอก
- **เข้าโปรแกรม IMC** เมื่อ BI < 15 หรือ BI ≥ 15 ที่ติ๊กว่ามี multiple impairment
- **กลุ่ม ADL** ติดสังคม ≥ 12 / ติดบ้าน 5 ถึง 11 / ติดเตียง 0 ถึง 4
- **ครบ 6 เดือน** นับจากวัน Start ตาม `CONFIG.IMC_DURATION_DAYS` (183 วัน)
- **จำนวนครั้งที่ได้ PT** นับจากรายการติดตามที่ประเภทเป็น PT

## ข้อจำกัดที่ควรรู้

- Google Sheet ไม่ใช่ฐานข้อมูล ระบบใช้ `LockService` กันสองคนบันทึกชนกันแล้ว
  แต่ถ้าในอนาคตมีผู้ใช้มากขึ้นหรือต้องการ audit log เต็มรูปแบบ ควรย้ายไปฐานข้อมูลจริง
- ข้อมูลที่นำเข้าจากไฟล์เดิมมีเฉพาะคะแนน BI รวม ไม่มีคะแนนราย 10 ข้อ
  แถวเหล่านั้นจะมีหมายเหตุกำกับไว้ว่านำเข้ามา
- ชีต `summary` ตั้งใจให้ดูอย่างเดียว ถ้าพิมพ์ทับสูตรจะเสีย ให้แก้ผ่านแอปเท่านั้น
- พิมพ์ได้เฉพาะหน้าแดชบอร์ดกับหน้ารายงาน ยังไม่มีฟังก์ชันพิมพ์ฟอร์มผู้ป่วยเป็น PDF
  เพราะทีมแจ้งว่าไม่ต้องใช้กระดาษแล้ว กดปุ่ม PDF จากหน้าอื่นจะถามก่อนว่าจะไป
  พิมพ์แดชบอร์ดแทนไหม ไม่ใช่พาไปแล้วสั่งพิมพ์เงียบ ๆ อย่างที่เคยเป็น
  ถ้ากดจากหน้ารายชื่อจะบอกด้วยว่าใช้ปุ่มส่งออกรายชื่อในหน้านั้นได้ตรงกว่า

## ใช้งานบนมือถือให้เหมือนแอป

Apps Script วาง `manifest` กับ service worker เองไม่ได้ เพราะหน้าจอจริงถูกฝังใน iframe
บนโดเมน `googleusercontent.com` ส่วนหน้าบนสุดเป็นของ `script.google.com` ซึ่งไม่ใช่ของเรา
เบราว์เซอร์อ่าน `manifest` จากหน้าบนสุดเท่านั้น ประกาศไว้ใน iframe จึงถูกเมิน
ส่วน service worker ต้องเป็นไฟล์ `.js` แยกบนโดเมนเดียวกัน แต่ `HtmlService` เสิร์ฟได้ทีละหน้า HTML

จึงแยกเป็นสองชั้น

### ชั้นที่ 1 — ในตัวแอปเอง (ใช้ได้ทันที ไม่ต้องตั้งอะไร)

- `WebApp.gs` ใส่ `apple-mobile-web-app-capable` ไว้ **iPhone / iPad** ที่กด
  ปุ่มแชร์ของ Safari → **เพิ่มไปยังหน้าจอโฮม** จะเปิดเต็มจอ ไม่มีแถบที่อยู่เว็บคร่อม
  (ใครเพิ่มไอคอนไว้ก่อนหน้านี้ต้องลบแล้วเพิ่มใหม่ iOS อ่านค่านี้ตอนกดเพิ่มเท่านั้น)
- เปิดแอปแล้วเห็นโครงหน้าจอทันที ไม่ต้องรอ `apiBootstrap` ที่กินเวลาหลายวินาที
- เน็ตหลุดแล้วขึ้นแถบเตือนค้างไว้ พร้อมบอกตรง ๆ ว่าที่กดบันทึกไปยังไม่ลงชีต
- **Android ไม่ได้อะไรจากชั้นนี้** Chrome เลิกใช้ `mobile-web-app-capable` ไปแล้ว
  ดู `manifest` อย่างเดียว ซึ่งใส่ไม่ได้

### ชั้นที่ 2 — เปลือก PWA ในโฟลเดอร์ `pwa/` (สำหรับ Android)

หน้า static เล็ก ๆ ที่ถือ `manifest` ไอคอน และ service worker แทนตัวแอป
เอาไปวางบน GitHub Pages แล้ว Android จะกด **ติดตั้งแอป** ได้จริง ได้ไอคอนจริง
เปิดแล้วเด้งเข้าลิงก์ `/exec` ให้เอง

เลือกวิธี **เด้งออกไปที่ลิงก์จริง** ไม่ใช่ฝัง iframe ไว้ในเปลือก เพราะแอปใช้อีเมลผู้ใช้
ตัดสินสิทธิ์ (`currentUser_` ใน `Api.gs`) ถ้าฝัง iframe การล็อกอิน Google จะต้องพึ่ง
third-party cookie ซึ่ง Safari บล็อกอยู่แล้ว เสี่ยงเข้าไม่ได้ทั้งที่ควรมีสิทธิ์
แลกกับการที่เปิดแล้วยังเห็นแถบชื่อเว็บบาง ๆ ค้างด้านบน

**วิธีเปิดใช้**

1. push โค้ดขึ้น GitHub ให้เรียบร้อย
2. ที่ repo บน GitHub เลือก **Settings → Pages → Build and deployment**
   ตั้ง Source เป็น *Deploy from a branch* แล้วเลือก branch `main` โฟลเดอร์ `/ (root)`
   (ไฟล์ว่างชื่อ `.nojekyll` ที่รากโปรเจกต์บอกให้ Pages เสิร์ฟไฟล์ตามที่เป็น
   ไม่ต้องเอา Jekyll มาแปลงก่อน ห้ามลบ)
3. รอสักครู่แล้วเปิด `https://manitsrik.github.io/Intermediate-Care-V0/pwa/`
4. บอกทีมให้เปิดลิงก์นั้นในมือถือ แล้วกดติดตั้งตามที่หน้านั้นบอก

**ก่อนใช้ต้องรู้** ลิงก์ `/exec` จะกลายเป็นของสาธารณะ เพราะฝังอยู่ในไฟล์ที่ Pages เสิร์ฟ
ตัวข้อมูลยังปลอดภัยเพราะ `currentUser_` โยน error ทิ้งทุกอีเมลที่ไม่มีในชีต `users`
แต่ต้องระวังว่า **ห้ามปล่อยให้ชีต `users` ว่างเปล่า** เพราะโค้ดถือว่ากำลังติดตั้งระบบอยู่
แล้วเปิดให้บัญชี Google ใดก็ได้เข้ามาเป็นผู้ดูแล

**เวลาแก้ไฟล์ในโฟลเดอร์นี้**

- แก้ลิงก์ปลายทาง แก้ที่ `APP_URL` ใน `pwa/index.html` ตัวเดียว
- แก้อะไรก็ตามใน `pwa/` ต้องขยับเลข `CACHE` ใน `pwa/sw.js` ด้วย
  ไม่งั้นเครื่องที่ติดตั้งไปแล้วจะยังเปิดของเก่าค้าง
- ทดลองบนเครื่องก่อนด้วย `node tools/serve-pwa.js` แล้วเปิด `http://localhost:8080`
  (ต้องเป็น localhost เท่านั้น service worker ไม่ทำงานบน `file://` และไม่ทำงานบน IP วงแลน)
- ไอคอนสร้างใหม่ได้เสมอด้วย `node tools/make-icons.js` ไม่ต้องเก็บไฟล์จากโปรแกรมวาดรูป

**ที่ยังทำไม่ได้แม้มีเปลือกแล้ว** คือใช้งานตอนไม่มีเน็ต ข้อมูลทุกอย่างวิ่งผ่าน
`google.script.run` ซึ่งต้องต่อเน็ตเสมอ เปลือกช่วยแค่ให้เปิดขึ้นมาแล้วเจอหน้าบอกสาเหตุ
แทนหน้า error ของเบราว์เซอร์

## ดูหน้าจอบนเครื่องก่อน deploy

มีสองวิธี ใช้คนละจุดประสงค์

### 1. พรีวิวบนเครื่อง — เร็วที่สุด ไม่แตะ Google เลย

```
node tools/build-preview.js
```

แล้วเปิด `preview/index.html` ในเบราว์เซอร์ ไม่ต้องมีเซิร์ฟเวอร์

ตัวพรีวิวประกอบจาก `css.html` กับ `js.html` ตัวจริง หน้าตาจึงตรงกับของที่ deploy
ส่วนฝั่งเซิร์ฟเวอร์แทนด้วยข้อมูลปลอม 6 เคสในหน่วยความจำ กดเพิ่ม แก้ ประเมิน BI
ได้ครบทุกหน้าจอ แต่ปิดหน้าต่างแล้วข้อมูลหายไป ไม่แตะ Google Sheet

เหมาะกับการดูดีไซน์ ทดลองกดใช้ และดูหน้าจอมือถือ (ย่อหน้าต่างหรือใช้โหมด
device toolbar ของเบราว์เซอร์) ไม่เหมาะกับการทดสอบตรรกะที่คุยกับ Google Sheet

### 2. ลิงก์ทดสอบของ Apps Script — ของจริงทุกอย่าง ยกเว้นทีมยังไม่เห็น

Apps Script สร้าง deployment ทดสอบไว้ให้ตั้งแต่ต้น ลิงก์ลงท้ายด้วย `/dev`
แทนที่จะเป็น `/exec` ดูรหัสได้จาก

```
npx @google/clasp list-deployments
```

ตัวที่ขึ้น `@HEAD` คือ deployment ทดสอบ ลิงก์คือ
`https://script.google.com/macros/s/<รหัสนั้น>/dev`

- แสดงโค้ดล่าสุดเสมอทุกครั้งที่ `clasp push` โดยที่ลิงก์ `/exec` ของทีมไม่ขยับ
- เปิดได้เฉพาะบัญชีที่มีสิทธิ์แก้ไขสคริปต์
- **ใช้ Google Sheet ใบเดียวกับตัวจริง** กดบันทึกแล้วข้อมูลลงชีตจริง

### ลำดับการทำงานที่แนะนำ

1. แก้โค้ด แล้ว `node tools/build-preview.js` ดูหน้าตาก่อน
2. `clasp push` แล้วเปิด `/dev` ทดสอบกับข้อมูลจริง
3. พอใจแล้วค่อย `clasp create-deployment --deploymentId <รหัสเดิม>` ทีมถึงจะเห็น
